# Decisions

One line per decision, newest at the bottom. Format: date, task, decision and why.

- 2026-11-16 · Task 1 · pnpm 10 workspaces with no Turborepo or Nx; `pnpm -r` is enough for six packages, and the stack list has no build orchestrator.
- 2026-11-16 · Task 1 · Node 24 LTS, pinned in `.nvmrc` and `engines`; pnpm pinned through `packageManager` so Corepack installs the same version everywhere.
- 2026-11-16 · Task 1 · TypeScript 6.0, not 7: typescript-eslint does not yet support 7. Strict plus `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` and `erasableSyntaxOnly`.
- 2026-11-16 · Task 1 · Workspace packages export their TypeScript source directly (no build step); Node's built-in type stripping runs the worker, so there is no tsx or ts-node.
- 2026-11-16 · Task 1 · ESLint 9 (flat config, typescript-eslint strict, eslint-config-next for `apps/web`) and Prettier; ESLint 9 because the Next.js plugins do not yet support 10. Approved as additions to the stack.
- 2026-11-16 · Task 1 · Prettier skips Markdown, so the hand-written docs keep compact tables.
- 2026-11-16 · Task 1 · `compose.yaml` at the root only includes `infra/docker-compose.yml`, so `docker compose up` works from the root and the services still live in `infra/`.
- 2026-11-16 · Task 1 · Local Postgres is 17 (a version Azure Database for PostgreSQL Flexible Server offers); the non-`BYPASSRLS` app role is left to task 2.
- 2026-11-16 · Task 1 · Local Temporal is the `temporalio/temporal` CLI dev server with a SQLite file on a volume, so workflow history survives restarts.
- 2026-11-16 · Task 1 · All images and npm packages pinned to exact versions; every compose service has a healthcheck so `docker compose up --wait` works in CI.
- 2026-11-16 · Task 1 · `postgres` (postgres.js) as the Postgres driver: Drizzle supports it and it has no native build step.
- 2026-11-16 · Task 1 · `pnpm test` includes an integration project that checks Postgres, Temporal and Azurite; `pnpm test:unit` runs without services.
- 2026-11-16 · Task 1 · CI is one GitHub Actions job on every PR and push to main: format check, lint, typecheck, test against the compose stack, build.
- 2026-11-16 · Task 1 · PLAN.md made generic: no client or personal names, in line with the hard constraint.
- 2026-11-16 · Task 2 · Tables: `tenants`, `users`, `documents`, `jobs`, all with `tenant_id` and UUID keys; `jobs.agent_version` is required from the start. Emails are unique per tenant regardless of case.
- 2026-11-16 · Task 2 · Foreign keys between tenant-owned tables include `tenant_id`, because foreign-key checks bypass RLS; this stops a row pointing at another tenant's row.
- 2026-11-16 · Task 2 · `users` holds tenant members only (`tenant_admin`, `tenant_user`); how operators are stored is decided in task 3, rather than a table with a null `tenant_id`.
- 2026-11-16 · Task 2 · RLS is enabled and forced on every table with one permissive `tenant_isolation` policy: `tenant_id = (SELECT app.current_tenant_id())`. The subquery makes Postgres evaluate the function once per query, not per row.
- 2026-11-16 · Task 2 · Roles, RLS and policies live in hand-written SQL migrations; Drizzle generates only the table migrations.
- 2026-11-16 · Task 2 · Two roles: `agentcore_owner` runs migrations and, like the Azure admin, is not a superuser (locally and in CI too); `agentcore_app` (no superuser, no BYPASSRLS, owns nothing) is what the app uses. The migration creates `agentcore_app` without a login if missing and checks its attributes rather than setting them, because a non-superuser cannot name SUPERUSER or BYPASSRLS from Postgres 16.
- 2026-11-16 · Task 2 · The app role can read `tenants` but not create them; creating tenants is an operator action for task 3.
- 2026-11-16 · Task 2 · `withTenant(tenantId, fn)` is the only query path exported by `@agent-core/db`; it validates the UUID, refuses to run as a role that can bypass RLS, owns tables or can switch to such a role, and sets a signed tenant for that one transaction.
- 2026-11-16 · Task 2 · Signed tenant context (replaces the earlier "known limit" after the independent review showed one injected SELECT could switch tenant): `withTenant` sets `app.tenant_id` and `app.tenant_sig` = HMAC-SHA256 of tenant, backend PID and transaction start time. `app.current_tenant_id()` (SECURITY DEFINER, fixed search_path) verifies it with a key the app role cannot read and raises `invalid tenant context` otherwise, so injected `set_config` fails and signatures cannot be replayed on another connection or transaction.
- 2026-11-16 · Task 2 · The isolation test creates a fresh database per run as the non-superuser owner, seeds two tenants and attacks as the app role, including injected `set_config`, forged and replayed signatures. It also fails if any relation the app role can use is not a public table with `tenant_id` and forced RLS, if a table has any policy other than the one `tenant_isolation` policy, or if a foreign key lacks `tenant_id`.
- 2026-11-16 · Task 2 · The signing key is `TENANT_CONTEXT_KEY` (base64, at least 32 bytes) for the app, from Key Vault in Azure, and the same key in `app.tenant_context_key` for the database, set with `pnpm db:set-context-key`. Rotating it means updating both together.
- 2026-11-16 · Task 2 · The hard constraint reads "every table that holds tenant data has `tenant_id`". `app.tenant_context_key` holds one key shared by all tenants, so a `tenant_id` there would mean nothing; it is system configuration in the `app` schema, which the app role cannot access. Per-tenant keys were considered and not adopted (`tenant_id` would only be a lookup column, at the cost of key rows per tenant).
- 2026-11-16 · Task 2 · pgcrypto (in its own `extensions` schema) provides HMAC in the database. Azure Database for PostgreSQL needs it allow-listed in the `azure.extensions` server parameter; task 6 sets that in Bicep.
- 2026-11-16 · Task 2 · TEMPORARY on the database and CREATE on `public` are revoked from PUBLIC, and the migration fails if the app role can still create either, so a temporary table can never shadow a tenant table.
- 2026-11-16 · Task 2 · FORCE RLS applies to the owner in Azure and now locally, so any data migration or backfill must set a signed tenant context per tenant; schema migrations are unaffected.
- 2026-11-16 · Task 2 · Accepted: primary keys are global, so inserting with another tenant's random UUID reveals that it exists. IDs are always generated by the server and never accepted from clients.
- 2026-11-16 · Task 2 · Planner statistics are gathered over all tenants, so EXPLAIN estimates could reveal another tenant's values. Text and content columns have `SET STATISTICS 0` (the isolation test checks every text column; new ones need the same). Accepted: total row counts per table (`pg_class.reltuples`, EXPLAIN) stay visible across tenants.
- 2026-11-16 · Task 2 · `withTenant` runs `RESET ALL` at the start of every transaction, then pins `search_path` (`public, pg_temp`), `row_security`, date, time zone and encoding settings locally, and opens the transaction read-write, so settings injected by one tenant on a pooled connection cannot affect the next.
- 2026-11-16 · Task 2 · Postgres always lets a role change its own defaults (`ALTER ROLE ... SET`). `withTenant` refuses to start if the app role has any such overrides; per-transaction settings make the important ones safe even before a restart.
- 2026-11-16 · Task 2 · `withTenant` also refuses roles with CREATEROLE, or that can create temporary or schema objects.
- 2026-11-16 · Task 2 · `app.current_tenant_id()` is `PARALLEL RESTRICTED`: parallel query stays available and the check runs in the leader, whose backend PID is the one signed.
- 2026-11-16 · Task 2 · The dev signing key in `.env.example` is public; the code refuses it for any database host other than localhost or the compose `postgres` service.
- 2026-11-16 · Task 2 · All tenants share one app role, so `pg_stat_activity` shows every tenant's query text. Values must always go as query parameters; `sql.raw` only ever takes constant SQL.
- 2026-11-16 · Task 2 · Accepted: the app role can create large objects (Postgres has no privilege to stop it). They hold no tenant rows; the risk is filling the disk, which monitoring in task 14 covers.
- 2026-11-16 · Process · Every PR gets an independent review from a fresh agent before it is opened; findings and outcomes go in the PR description (CLAUDE.md, How to work, step 4).
- 2026-11-16 · Task 3 · Auth.js v5 (5.0.0-beta.32, pinned) with JWT sessions in an encrypted cookie and no session table; approved while still labelled beta because it is the version built for the App Router.
- 2026-11-16 · Task 3 · Tenant users sign in at `/t/{slug}/sign-in`, so the tenant is known before any lookup; one email can belong to users of several tenants.
- 2026-11-16 · Task 3 · Slugs: 3 to 40 lowercase letters, digits and single hyphens, not a reserved route word; defaulted from the tenant name, chosen by the operator, fixed once created.
- 2026-11-16 · Task 3 · Sign-in pages look and behave the same for unknown slugs and for tenants with no linked Microsoft organisation, and never show the tenant name. Known limit: starting Microsoft sign-in for a tenant that has linked an organisation redirects to that organisation's Entra endpoint, which reveals that the tenant exists and its Entra tenant ID. Hiding that would need our own multi-tenant ID-token validation instead of Auth.js's; not adopted.
- 2026-11-16 · Task 3 · Slug to tenant ID is the one lookup before a tenant is known: `app.tenant_id_for_slug()` reads `app.tenant_slugs`, kept by a trigger on `tenants`, because FORCE RLS stops even the owner reading `tenants` without a tenant set. The directory holds routing data only and the app role cannot read it.
- 2026-11-16 · Task 3 · The app role may insert into `tenants`, but only inside the new tenant's own signed context (server-generated ID), so no special function is needed to create tenants.
- 2026-11-16 · Task 3 · Operators are not stored: they are members of the client's Entra organisation (`OPERATOR_ENTRA_TENANT_ID`) with the "Operator" app role. Sessions last 1 hour, so removing the role takes effect within the hour; MFA and device rules come from the client's Conditional Access.
- 2026-11-16 · Task 3 · Tenant sessions last 8 hours, and every protected request re-reads the user from the database, so removing a user or changing their role takes effect at once.
- 2026-11-16 · Task 3 · Microsoft sign-in goes to one organisation's own Entra endpoint (the tenant's linked organisation, or the client's for operators), because Auth.js's multi-tenant "organizations" issuer fails the ID token issuer check. The server action decides whether there is an organisation before calling Auth.js, so every "no organisation" case gets the same refusal page; the linked organisation is looked up only on the Auth.js sign-in and callback routes and in that action, never on ordinary requests. A sign-in scope cookie carries the scope to the callback; the sign-in rules re-check issuer, organisation and user, so the cookie grants nothing.
- 2026-11-16 · Task 3 · One linked Microsoft organisation per tenant for now (`tenant_entra_orgs` keyed on `tenant_id`); several would need the user to pick theirs before sign-in.
- 2026-11-16 · Task 3 · A Microsoft user is matched by Entra object ID. On first sign-in they are matched by email only when the token carries `xms_edov: true` (email domain verified by the organisation; an optional claim to enable on the app registration), which then records the object ID. Email without it, and `preferred_username`, are never used, because an admin of the linked organisation can set them to any address.
- 2026-11-16 · Task 3 · Email links use Auth.js's Credentials provider with our own single-use tokens (SHA-256 hash stored in the tenant, 15 minutes), not Auth.js's email provider, which needs a database adapter called before any tenant is known.
- 2026-11-16 · Task 3 · Opening an email link shows a "Sign in" button rather than signing in, so email security scanners that open links cannot use up the token.
- 2026-11-16 · Task 3 · Requesting a link answers the same way for unknown addresses, and the lookup and sending run after the response (`after()`) so timing does not reveal who is a user. Rate limiting is left to task 14.
- 2026-11-16 · Task 3 · Email goes through Azure Communication Services (`@azure/communication-email`); locally and in tests a `dev-outbox` transport writes messages to files and is refused unless `AUTH_URL` is local. The public dev `AUTH_SECRET` is refused the same way.
- 2026-11-16 · Task 3 · Access is checked in every page and API route (`lib/auth/guards.ts`); the proxy only redirects people with no session. Pages answer 403 with `forbidden()`, API routes 401 or 403.
- 2026-11-16 · Task 3 · The role-matrix test signs in with real Auth.js session cookies encrypted with the run's secret, so the app has no test-only way in. Playwright runs against the production build with a throwaway database.
- 2026-11-16 · Task 3 · `output: "standalone"` removed for now (`next start` does not support it); task 6 decides the container build.
- 2026-11-16 · Task 3 · Not verified in CI: a real Microsoft sign-in, which needs an Entra app registration. The sign-in rules are tested directly; the full flow is checked by hand when task 6 sets up the dev environment.
- 2026-11-16 · Task 3 · Guest accounts in a linked organisation (an `idp` claim different from the issuer) are refused: only the organisation's own members can sign in.
- 2026-11-16 · Task 3 · Using one email link deletes the user's other outstanding links.
- 2026-11-16 · Task 3 · Sessions are not revocable before they expire: sign-out clears the browser's cookie only. Tenant users are re-read on every request; operator sessions last at most 1 hour.
- 2026-11-16 · Task 3 · Accepted: login CSRF with email links (someone sends a victim a link to the sender's own account); the verify page shows "Continue as {email}". Binding a link to the requesting browser was considered and left for later.
- 2026-11-16 · Task 3 · Slugs are fixed and tenants are not deleted, enforced by triggers that apply to the owner too, so the slug directory cannot go stale. The database also rejects double hyphens; reserved words are checked in code.
- 2026-11-16 · Task 3 · `@azure/communication-email` was approved when task 3 was planned, to send email through Azure Communication Services as decided in PLAN.md.
- 2026-11-17 · Planning · Google Workspace approved as a second SSO option for tenants (Auth.js's built-in Google provider; no new package). Added as task 3b with one linked-SSO model and a per-tenant switch to turn off email links. Other identity providers (Okta, SAML) wait until a client asks.
- 2026-11-17 · Local dev · The compose Postgres listens on host port 5433, not 5432, so it does not clash with a Postgres already installed on the developer's machine.
- 2026-11-17 · Task 3b · One SSO link per tenant in `tenant_sso`: a Microsoft organisation or a Google Workspace domain, not both. It replaces `tenant_entra_orgs`; existing links are copied by the migration.
- 2026-11-17 · Task 3b · Tenant sign-in pages show one "Sign in with your work account" button that goes to whichever provider the tenant has linked, so users cannot pick the wrong one. Unknown tenants and tenants with nothing linked get the same refusal, without contacting Microsoft or Google.
- 2026-11-17 · Task 3b · Google sign-in requires a Google-issued token with `hd` (hosted domain) equal to the tenant's linked domain, `email_verified` true and the email in that domain. Google sets `hd` only for Workspace domains the organisation has verified, so personal Google accounts are always refused.
- 2026-11-17 · Task 3b · Google users are matched by Google ID (`sub`), or on first sign-in by email within the verified domain, which then records the Google ID.
- 2026-11-17 · Task 3b · No Google `hd` sign-in parameter: it would only steer Google's account picker and would put the tenant's domain in the redirect URL. The domain is enforced after sign-in. The redirect still shows that a tenant exists and uses Google, as it does for Microsoft.
- 2026-11-17 · Task 3b · A tenant admin can turn email links off at `/t/{slug}/admin/sign-in`, but only when the tenant's SSO is configured on the deployment and that admin has already signed in with it (an Entra object ID or Google ID is recorded), so at least one admin can still get in. Links already sent stop working, and a link request then emails a note to use the work account; the on-screen answer is unchanged, so it still reveals nothing about who is a user.
- 2026-11-17 · Task 3b · `pnpm tenant:sso` links SSO and switches email links on or off, until the operator console manages tenants; it is also how an operator recovers a locked-out tenant.
- 2026-11-17 · Task 3b · The SSO target is looked up only when an SSO provider is configured, so deployments without SSO make no lookup.
- 2026-11-17 · Task 3b · Accepted: turning email links off does not end sessions already started with a link; they last until they expire (at most 8 hours).
- 2026-11-17 · Task 3b · Accepted: a Google Workspace user whose primary email is on a secondary or alias domain is refused, because `hd` is the primary domain and the email must be in it. Linking secondary domains can come later if a tenant needs it.
- 2026-11-17 · Task 3b · Google Workspace domains must be well-formed (labels of letters, digits and inner hyphens), checked in code and by the database.
- 2026-11-17 · Windows · The Playwright setup starts Next.js with Node directly (no shell or pnpm wrapper) and stops it with `taskkill /T` on Windows, so `pnpm test:e2e` runs on Windows as well as Linux and macOS. `pnpm test:unit` quotes its argument with double quotes, which Windows' shell accepts.
- 2026-11-17 · Task 3b · Sign-in refusals are logged on the server with a fixed reason code, the tenant slug (or "operator console") and the provider, never the email address or token; slugs are only logged if well-formed, so a crafted value cannot forge log lines. Errors Auth.js raises itself are logged by error type only. Users still see only "Sign-in was refused."
- 2026-11-17 · Task 3b · `pnpm tenant:add-user` adds a user or admin to an existing tenant until the operator console and tenant admin pages manage users. Emails are stored lowercase; uniqueness per tenant (regardless of case) is left to the unique index, so concurrent adds cannot both succeed, and the error never repeats the raw database message. `tenant:create` checks the admin email before creating anything.
- 2026-11-17 · Task 3b · The setup commands share one wrapper: plain error messages, never a stack trace or raw database error, and the usage line for unknown options. Email addresses with control characters are refused everywhere, from one shared check in `@agent-core/db`.
- 2026-11-17 · Task 4 · Tenant documents go to Azure Blob Storage, one private container per tenant (`tenant-{tenant_id}`), each file at `documents/{document_id}`; a container per tenant would make deleting a tenant's files one operation (no such operation exists yet: see "Before production" in `docs/operations.md`) and allows per-tenant access rules or encryption later.
- 2026-11-17 · Task 4 · Container and blob names are built only from server-side IDs, in one module (`lib/documents/storage.ts`, now `packages/core/src/storage.ts`); the uploader's filename is kept on the record for display only (no path parts, no control characters, at most 200 characters). Blob Storage has no row-level security and one credential covers every tenant, so this is what keeps tenants' files apart.
- 2026-11-17 · Task 4 · Accepted types are PDF and Word (.docx), recognised by content, not name or browser type: PDF by `%PDF-` at the start; Word by reading the zip's central directory, which must hold `word/document.xml` and a `[Content_Types].xml` (inflated with a size cap) declaring the main part as a Word document. Macro-enabled documents, templates, macro parts under any name, encrypted entries and everything else are refused; old `.doc` and password-protected files get their own message. Extracting text from Word in task 9 will need a library not yet on the stack list.
- 2026-11-17 · Task 4 · Uploads are limited to `MAX_UPLOAD_MB` (25 by default). The body is read with a running byte count and reading stops as soon as the limit (plus 64 KB for the form) is passed, whether or not a length was declared; a declared oversize length is refused before reading. Each instance runs at most 4 uploads at once (others get "try again"), so upload memory stays bounded. Empty files are refused.
- 2026-11-17 · Task 4 · The file is written first, then the record in the tenant's signed context; if the record fails, the file is deleted again, and a failed delete is logged without hiding the original error. A crash between the two steps can still leave a file without a record; a clean-up job can sweep those later. Each file is stored with the detected type and `Content-Disposition: attachment`.
- 2026-11-17 · Task 4 · Tenant admins and tenant users can upload; operators cannot, since they belong to no tenant. Uploads go to `POST /api/t/{slug}/documents`, which answers JSON to API callers and redirects the portal's own form back to the documents page.
- 2026-11-17 · Task 4 · Uploads must come from the site itself: the route refuses any other `Origin`, on top of the session cookie being SameSite=Lax. Requests without an `Origin` (non-browser API clients) are allowed, since browsers always send one on POST.
- 2026-11-17 · Task 4 · Not in this task: downloading and viewing (task 11's review screen), deleting, and malware scanning (Microsoft Defender for Storage, set up in Azure in task 6 or 14).
- 2026-11-17 · Task 4 · Display filenames have control and text-direction characters removed, are cut at 200 characters without splitting a character, and get the extension of the detected type, so a name cannot pose as another kind of file.
- 2026-11-17 · Task 4 · Storage and database failures during an upload are logged by error type only and answered with a plain "upload failed" message.
- 2026-11-17 · Task 5 · Each upload creates a job (status `uploaded`) and starts a Temporal workflow with ID `job-{job_id}` and reuse policy "reject duplicate", so a job's workflow runs once, ever; once Temporal has it the status becomes `queued`. Starting waits at most 5 s for Temporal. If that fails, or the job record cannot be written, the upload still succeeds and the job stays `uploaded` (or is not created).
- 2026-11-17 · Task 5 · Workflow inputs carry the tenant and job IDs (and the retry policy) only, never document content; the worker reads the document and agent from the job's record inside the tenant's context, so a forged input cannot point a job at another document. Temporal's history (Temporal Cloud later) holds no tenant data.
- 2026-11-17 · Task 5 · The worker writes to the database as the app role through `withTenant`, like the web app, so row-level security applies to it too.
- 2026-11-17 · Task 5 · One `job_attempts` row per attempt (number, outcome, start and finish times, a short reason code; never an error message or document content). An attempt is only finished while still `running`, so a late attempt cannot rewrite one already closed; starting attempt N closes earlier ones left running as `timed-out`, and finishing the job closes any still running as `abandoned`. The job is `running` from its first attempt, then `succeeded`, or `failed` once retries run out, and never moves back.
- 2026-11-17 · Task 5 · Default retry policy: 3 attempts, waiting 5 s then 20 s (backoff ×4). Recording the final status retries until it succeeds, so a brief database outage cannot leave a job hanging.
- 2026-11-17 · Task 5 · Until task 7, jobs run a placeholder agent recorded as `skeleton` / `skeleton-1` that does no work. It can be told to fail its first attempts only when the worker runs with `ALLOW_TEST_FAULTS=true`, which the worker refuses unless Temporal and the database are local.
- 2026-11-17 · Task 5 · The job contract (task queue, workflow name, input shape, retry defaults, placeholder agent) lives in `@agent-core/core`, shared by the web app and the worker. The task queue is configurable (`JOB_TASK_QUEUE`); the e2e run uses a queue of its own so a developer's local worker cannot take its jobs.
- 2026-11-17 · Task 5 · A job's status page and API (`/t/{slug}/jobs/{id}`) show the agent and version and every attempt; jobs of other tenants are simply not found.
- 2026-11-17 · Task 5 · Activities turn every failure into a fixed message and reason code before it leaves them (raw errors can quote SQL parameters or, later, document content, and Temporal keeps failures in its history); the worker logs only the error type.
- 2026-11-17 · Task 5 · The final status is recorded even if the workflow is cancelled. A workflow terminated outright runs no more code, so its job keeps its last status.
- 2026-11-17 · Task 5 · Known limit, for task 14: a job left `uploaded` (Temporal unreachable at upload) or `running` (workflow terminated) is not picked up again automatically; a sweeper per tenant can restart it, which is safe because each job's workflow ID is fixed. Activities have no heartbeat yet, so a crashed worker's attempt is only retried after its 10-minute timeout; heartbeats come with real work in task 7.
- 2026-11-17 · Task 5 · `ALLOW_TEST_FAULTS` is refused unless Temporal and the database are on this machine (localhost only); service names such as `postgres` or `temporal` do not count, since deployed environments use them too.
- 2026-11-18 · Task 6 · The dev environment is one resource group, `rg-agent-core-dev`, first in UK South (moved to West Europe; see below), in a subscription of its own (separate billing, and nothing else in it to break); every resource is tagged `project=agent-core`, `env=dev`.
- 2026-11-18 · Task 6 · Temporal Cloud on the Developer plan (no base fee, usage plus 10%) for the hosted demo; the worker and web app connect with an API key over TLS (`TEMPORAL_API_KEY`). Self-hosting Temporal in a client's own Azure remains their choice, to be added as a later task.
- 2026-11-18 · Task 6 · Temporal Cloud's namespace is in AWS `eu-west-2` (London); its Azure regions are US and Australia only, in preview. This is the one service outside Azure, and it holds no tenant data: workflow inputs are tenant and job IDs, and failures are fixed messages and reason codes.
- 2026-11-18 · Task 6 · GitHub Actions deploys with OpenID Connect (a federated credential on a managed identity, no stored secret), limited to the `dev` GitHub environment (which only `main` may deploy to) and to the resource group: Contributor plus a Role Based Access Control Administrator assignment conditioned to the five roles the templates grant, to managed identities only. The deploy identity itself lives in a separate resource group, so it cannot change its own access.
- 2026-11-18 · Task 6 · Private network: Container Apps and Postgres in one virtual network, the database with no public address. Migrations therefore run as a Container Apps job inside it (the worker image running `packages/db/src/deploy-cli.ts`), and one-off admin commands through an admin job.
- 2026-11-18 · Task 6 · On each deploy the migrate job creates the database if missing (so the migrating admin owns it), applies migrations, gives `agentcore_app` its login and password, and stores the tenant context key; every step is safe to repeat, tested against a fresh Postgres with a non-superuser admin.
- 2026-11-18 · Task 6 · Secrets live in Key Vault. Generated ones (database passwords and URLs, tenant context key, Auth.js secret) are created once by `infra/azure/ensure-secrets.sh` and never overwritten; the email connection string is written by Bicep; the Temporal API key and SSO client secrets are added by hand. Container Apps read them as Key Vault references. Values are written from a private temporary file, never on a command line.
- 2026-11-18 · Task 6 · Blob Storage is reached with the app's managed identity (`@azure/identity`, approved), with shared keys disabled on the account and no public blobs.
- 2026-11-18 · Task 6 · The web app scales to zero when idle (the first request after a quiet spell waits a few seconds); the worker always runs one copy, since it polls Temporal.
- 2026-11-18 · Task 6 · Images: the web app as a Next.js standalone server (switched on only for the image build), and the worker running its TypeScript directly with the workspace layout kept; both built and pushed by the deploy, tagged with the git commit.
- 2026-11-18 · Task 6 · Two managed identities: the web app and worker run as the app identity, which may read only its own secrets, granted one by one; the migrate and admin jobs run as an ops identity, the only one that can read the database admin credentials.
- 2026-11-18 · Task 6 · Blob Storage accepts traffic only from the apps' subnet (a service endpoint and a network rule), on top of managed-identity access. Key Vault and the container registry stay public, because the CI runners (GitHub's, or the `CI_RUNNER` provider's) write to them, and accept only Entra sign-ins with the right role.
- 2026-11-18 · Task 6 · Deploys run in two passes: infrastructure and jobs first (apps unchanged), then the migrate job, then the apps on the new image, so a release never runs against an unmigrated database.
- 2026-11-18 · Task 6 · The app role's password is set as a SCRAM-SHA-256 verifier computed in the migrate job, so the plain password never reaches Postgres statement statistics or logs.
- 2026-11-18 · Task 6 · The admin job takes its command and arguments as environment variables (`ADMIN_COMMAND`, `ADMIN_ARGS` as a JSON array) and runs the same tenant CLIs, so arguments never clash with the Azure CLI's own options.
- 2026-11-18 · Task 6 · `/api/ready` (public, no details) checks the app can use its database as the app role; the deploy checks it, while container probes keep using `/api/health` so a database blip does not restart the app.
